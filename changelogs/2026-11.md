# November 2026

## 2026-11-13

- Large `"edge-t"` layouts can use workers. `computeMultilevelForcePositionsAsync()` from `@yggy-tech/graphraum/layout-multilevel` refines the big levels in parallel, 1.7 times faster for that step at 1,000,000 nodes, with the same layout quality. Without workers it runs on one thread. A warm start of the multilevel layout now settles only what changed (new nodes, changed edges or anchors) and leaves every other node where it was ([#241](https://github.com/yggy-tech/graphraum/issues/241)).
- Huge graphs can now open straight into the cluster view. `openClusterLod()` from `@yggy-tech/graphraum/lod` takes plain typed arrays (positions, edge pairs, optional colours), builds the tree in a Web Worker without blocking the page, and hands graphraum only the cut, so the full graph is never loaded into the renderer. The coarse regions appear first, in about 0.2 seconds at 1,000,000 nodes, and the edges between them follow. Without a worker it does the same on the page's own thread. Real nodes come from a function you pass, and the whole graph stays in compact arrays, so millions of nodes fit. See the Cluster LOD guide and `bun run dev:lod` with `?n=5000000`.
- Very large graphs use far less memory. The edge buffers now hold only the edges that are drawn, not room for every curve of every edge, so a 100k node graph keeps about 300 MB less in memory and its first frame arrives about four times sooner. A graph of 5 million nodes and 15 million edges now loads in 2D instead of crashing the tab. The graph keeps your node and edge objects instead of copying them, so change them with `updateNodes()` rather than editing them after `setData()` ([#136](https://github.com/yggy-tech/graphraum/issues/136)).
- Cluster level of detail looks and feels finished. Glyphs are bigger and carry a compact member count (1.2k, 34k) that hides when the glyph is too small; they blend the colours of their members as soft blobs; a click on a glyph zooms in on it; and a cluster that splits or merges animates in about 200 ms, or swaps at once with reduced motion on. Changing the cut now applies only the nodes and edges that arrived or left. Nodes can also show up to three colours through the new `blend` field. Run `bun run dev:lod` to try it on 200,000 nodes ([#229](https://github.com/yggy-tech/graphraum/issues/229)).
- Added an optional cluster level of detail for very large graphs, in its own entry `@yggy-tech/graphraum/lod`. It groups nearby nodes once, then on every camera change draws far regions as one glyph sized by how many nodes it holds, joined by aggregated edges, and opens the regions you zoom into until you see the real nodes. What is drawn stays within a budget you set (4,000 nodes and 8,000 edges by default) however large the graph is, in 2D and 3D, so a million-node graph shows every region instead of the first 100,000 nodes. Apps that do not use it pay nothing in the main bundle. The look of the glyphs is provisional. See the new Cluster LOD guide ([#229](https://github.com/yggy-tech/graphraum/issues/229)).
- Added an opt-in multilevel force layout for large graphs ([#238](https://github.com/yggy-tech/graphraum/issues/238)). `computeMultilevelForcePositions()` from the new `@yggy-tech/graphraum/layout-multilevel` entry lays out a few hundred merged groups first, then refines finer levels, and can hand you a rough picture of the whole graph before the refinement finishes. With `layoutStyle: "edge-t"` it was about 2.5 to 3 times faster at 10,000 and 100,000 nodes at similar layout quality; `"classic"` is already fast and gains nothing. Predefined starts, anchors and clusters carry through, and the default layout and the main bundle do not change. See the Layout guide.

## 2026-11-12

- Loading a large graph is faster. `setData()` and the first frame take about half the time on a 30,000 to 100,000 node graph, and about a third less at 300,000 nodes: the graph is read in one pass, the camera fit no longer lays out the view twice, and a window resize that does not change the size no longer redraws it. What is drawn does not change.
- Panning and zooming a large 2D graph does less work again. Edges that stay in view are no longer rewritten on every camera move, only the ones that come into view or leave it. What is drawn does not change; where edges overlap, their paint order can differ ([#235](https://github.com/yggy-tech/graphraum/issues/235)).
- Panning and zooming a large 2D graph does less work per frame. Finding the nodes in view is about 12 times faster at 100,000 nodes, and nodes that stay in view are no longer rewritten on every camera move, only the ones that enter or leave. What is drawn does not change ([#228](https://github.com/yggy-tech/graphraum/issues/228)).

## 2026-11-11

- Large graphs keep their important edges in the overview. When more edges are in view than `maxVisibleEdges`, graphraum used to keep an even sample. It now keeps the edges of selected, focused and hovered nodes first, then the edges between the best-connected nodes, so hubs and the main structure stay visible while you pan. In 2D it also skips edges shorter than a pixel, which add nothing to the picture. `getDiagnostics()` has a new `subPixelEdgesSkipped` count ([#227](https://github.com/yggy-tech/graphraum/issues/227)).
- Added an optional interaction quality mode for large graphs. Turn it on with `interactionQuality: { enabled: true }` or `setInteractionQuality()` and graphraum draws at a lower resolution and shows fewer edges (in 2D also fewer nodes) while the camera moves and frames run slow, then restores full quality in one frame about 200 ms after the camera rests. Your data never changes, no draw call is added, and a graph that keeps up stays at full quality. `getDiagnostics().interactionQuality` reports the tier. It is off by default ([#226](https://github.com/yggy-tech/graphraum/issues/226)). See the Camera and 3D guide.
- Selecting, focusing or hovering a node in a large graph no longer redraws the whole edge list. Over the edge budget, graphraum used to repack every visible edge on each change, about 450 ms at 900,000 edges in a test run. The budgeted edges are now independent of the selection, and the edges of the selected node that the budget left out are drawn as a small extra layer, under a millisecond. They are still always visible.

## 2026-11-10

- **Breaking:** the force layout moved to its own entry, `@yggy-tech/graphraum/layout`. Import `computeForcePositions`, `computeClusteredForcePositions`, `createForceSimulation`, `DEFAULT_FORCE_SETTINGS`, `FORCE_LAYOUT_STYLES`, `forceIterationCount` and the `Force*` types from there instead of `@yggy-tech/graphraum`. Apps that only render get a 5.7 KiB (gzip) smaller main bundle, and the main entry has room again for new features.
- A layout no longer starts over when a graph gains nodes. Pass the previous positions as `initialPositions` with `warmStart: true` to `computeForcePositions()` or `createForceSimulation()`, and use the new `placeNewNodes()` from `@yggy-tech/graphraum/layout-start` to put new nodes next to their neighbours (or their cluster): known nodes keep their place and the layout only settles briefly, so existing nodes barely move. It works with both layout styles, clusters and anchors. The Layout guide also explains when a layout computed on your server is the better choice ([#147](https://github.com/yggy-tech/graphraum/issues/147)).
- Small clusters now sit closer to the rest of a clustered layout. Before, a group of 2% of the nodes kept an empty margin 4 times (`"classic"`) to 12 times (`"edge-t"`) wider than a large group. Cluster centres are now spaced by cluster size, and `"edge-t"` scales the push between clusters by size. The margin is now 2.6 and 8.9 times wider, and groups stay as clean as before ([#192](https://github.com/yggy-tech/graphraum/issues/192)).

## 2026-11-07

- Added an optional focus lens. Turn it on with `focusLens: { enabled: true }` or `setFocusLens()` and nodes near the center of the canvas draw larger while nodes toward its edge draw smaller, in 2D and 3D. Labels from `GraphraumOverlay` fade in only on the large ones. Positions never move, picking follows the drawn size, and a hovered or selected node never shrinks. It is off by default.
- You can now change how a graph looks beyond colours. Pass `style` to the constructor or call `setStyle()` to set a default node stroke width, a default arrowhead size and label typography, and switch between ready-made looks without rebuilding the graph. `@yggy-tech/graphraum/styles` ships `neutral` (greys with blue accents for hover and selection, on a transparent canvas with a system font), `blueprint`, and `classicDark` and `classicLight`, which are exactly the looks graphraum has always had. Labels get `--graphraum-label-*` CSS custom properties you can use in your own label styles. The default look does not change, and drawing cost stays the same ([#203](https://github.com/yggy-tech/graphraum/issues/203)). See the new Styling guide.
- Nodes can show an icon. Build an atlas from SVG strings with `createIconAtlas()` from `@yggy-tech/graphraum/icons` (it includes a helper for raw Phosphor SVGs, and no icon set is bundled), pass it to `graph.setIconAtlas()`, and give nodes an `icon` index. Icons are tinted, sit inside the node in lit and toon shading and in 3D, and cost no extra draw call. The Data and visuals guide has a new Icons section ([#208](https://github.com/yggy-tech/graphraum/issues/208)).
- You can now check which groups in a drawing are real. `measureLayoutStability()`, imported from `@yggy-tech/graphraum/diagnostics` so it stays out of the main bundle, lays the graph out with several seeds and reports how stable each cluster is, next to the score of a shuffled copy of the graph that has the same node degrees but no real groups. A cluster is trustworthy when it scores clearly above that shuffled copy. The Prove run reports the score for its fixture ([#194](https://github.com/yggy-tech/graphraum/issues/194)).
- Long chains and strips no longer start knotted. Force layouts take an optional `initialPositions` start, and the new `@yggy-tech/graphraum/layout-start` entry computes one from graph distances, so the layout starts stretched along the graph's length. On a long grid strip the layout comes out with almost no folds where the default random start leaves dozens or hundreds. The default start is unchanged and the main bundle barely grows ([#193](https://github.com/yggy-tech/graphraum/issues/193)).
- Force layouts can follow positions you already have. Pass `anchors` to `createForceSimulation()` with one position per node, for example a PCA or UMAP projection of embeddings, and nodes start there and are pulled back towards it. The positions can use any range, nodes with `NaN` are laid out freely, and `settings.anchorStrength` sets how closely the layout follows them. The new Guided layout guide shows how to combine anchors, clusters, and weak neighbour edges ([#170](https://github.com/yggy-tech/graphraum/issues/170)).

## 2026-11-06

- Force layouts have a second style for graphs that end up as one tangled ball. Set `layoutStyle: "edge-t"` in `ForceSettings` to give well-connected nodes more room, so groups separate and hubs no longer pile up in the middle. It works for `computeForcePositions()`, clustered layouts and `createForceSimulation()`, and a running simulation can switch with `setSettings({ layoutStyle: "edge-t" })` without starting over. Its one-shot layout runs 8 times as many steps, so run large graphs in a worker. `"classic"` stays the default ([#191](https://github.com/yggy-tech/graphraum/issues/191)).
